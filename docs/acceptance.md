## 已定位并修复的问题

1. 触发器索引 `Vec<usize>` 的批量 Hash 使用宿主位宽。定位时两端完整权威存档 1,890,725 字节相同，13 组所有者仅触发器哈希不同；已固定为原生 64 位小端编码，保留 Mac 既有哈希流。
2. 桥接层重复发布生产事件，提前消耗完成标记，导致 GI 留在 limbo；已改为由 `SimRuntime` 原有 admission 流程唯一发布并执行 PLACE。实际 GI、坦克出厂已验证。
3. 退出/重入时的旧 Worker 和旧 socket 异步回调可能影响新对局；已加入 generation、引擎实例和连接身份校验。
4. Safari 在大地图的原生区域填充递归中耗尽机器调用栈。根据实际 Worker 错误栈定位 `flood_fill_node_index`，改为保持原遍历顺序的显式 DFS 帧。`npm run test:zone-fill` 从固定上游只读提取原函数，**20,000 组随机地形的节点、返回值、边登记顺序全部一致**，30,000 行连通区压力通过。补齐 11 份固定上游 JSON 后，原有 **98 项 zone 回归全部通过**。

## 同步和源目录边界

固定快照：VERA `5450e8a7f7b5f04d88071171f8d72b6bc9091a9f`；WERHD 参考 `2ac47a5d6b1891f3c5e60795f51ce2c5c73ca4ed`。

`sync:check → sync:upstream → sync:check` 已实际通过暂存、补丁应用和固定版本重建。相同内容保持 vendor 文件 mtime，避免无谓编译。所有本任务写入、构建缓存、生成文件和 Git 提交均在 `werhd-vera`，原始两个项目只读。

WERHD 的基线文件指纹一致。VERA 原目录在任务期间出现并行 Android 工作，HEAD 从 `5450e8a7` 推进到 `7d5c20dd`，审计时有 46 个文件不同。因此 `check:isolation` 如实报告上游漂移，未重置/覆盖原目录，也未重录基线隐藏差异。明细在 `validation/isolation.json`。本项目始终保留开始时的固定快照，升级必须显式执行 `sync:upstream -- --update` 并重新验收。
